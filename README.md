# FTC DECODE Robot Code · 2025–26

**Written by Bryan Pan** · FTC Team 5214

Robot code for a FIRST Tech Challenge **DECODE** (2025–26) robot: a mecanum drivetrain with a two-motor **catapult** launcher and a roller **intake**. It uses [Pedro Pathing](https://pedropathing.com/) for path following and localization, and Pedro's **Ivy** command library to organize subsystem behavior.

This project is **forked from the [Pedro Pathing Quickstart](https://pedropathing.com/)**. Everything in the `pedroPathing/` folder comes from the Quickstart. All other code (subsystems, commands, TeleOp and autonomous OpModes) was written by me.

> I'm sharing this so other teams can use it and learn from it. If you use it, a credit back to this repo is appreciated!

## What is FTC?

[FIRST Tech Challenge](https://www.firstinspires.org/robotics/ftc) (FTC) is a robotics competition for middle and high school students. Every season a new game is announced, and teams have a few months to design, build and program a robot to play it.

Matches are played by two alliances, **red and blue**, with two teams on each. Every match has two parts:

- **Autonomous (30 seconds):** the robot drives itself using only pre-written code and its sensors. This is where path following and localization matter most.
- **Driver-controlled (2 minutes):** students drive the robot with gamepads, and the code helps them with things like field-centric driving and automated movements.

Robots run Java on an Android-based Robot Controller, using the official FTC SDK.

In the **2025–26 game, DECODE**, robots pick up balls called *artifacts* and launch them into their alliance's goal. They can also open a gate to release scored artifacts, and they return to their base at the end of the match. This robot collects artifacts with a roller intake and launches them with a catapult.

---

## Features

- **Pedro Pathing** autonomous routines on both alliances, including 9- and 12-artifact autos
- **Command-based structure** (Ivy `Command`s + `Scheduler`) for the intake and catapult
- **Pose hand-off from auto to TeleOp**: the robot's final auto pose and alliance carry into TeleOp, so field-centric driving and auto-align work right away
- **TeleOp auto-drive shortcuts**: hold a button to drive automatically to the launch spot, the human player station, or the gate
- **Field-centric / robot-centric toggle**
- **Catapult stall protection**: the return motor cuts power after 5 s if the arm can't get back down
- **Alliance mirroring**: red paths are generated by mirroring the blue poses (`Pose.mirror()`), so one set of coordinates covers both sides

## OpModes

### TeleOp

| OpMode | Description |
|---|---|
| `TeleOpMain` | Competition TeleOp with auto-drive shortcuts |
| `TeleOpManual` | Backup TeleOp: driving, intake and catapult only, no auto-drive |
| `CatapultTest` | Runs only the catapult and shows its encoder value |
| `IntakeTest` | Runs only the intake |
| `Tuning` | Pedro Pathing tuning menu (localization, velocity, zero-power acceleration, PIDF tuners, test paths) |

### Autonomous

All autos start from the goal side (`Poses.startPoseGoal`) except `RedTaxi`.

| OpMode | Alliance | Description |
|---|---|---|
| `BlueAuton12` / `RedAuton12` | Blue / Red | Score preloads, then intake and score spike marks 2, 1 and 3, with a gate clear after spike 2 |
| `BlueAuton9` / `RedAuton9` | Blue / Red | Score preloads, then spike marks 2 and 1 (with gate clear), then park |
| `RedTaxi` | Red | Drives off the far start line toward the human player station for leave points |

## Driver controls (Gamepad 1)

| Input | Action |
|---|---|
| Left stick | Drive (translate) |
| Right stick X | Turn |
| Left trigger | Run intake |
| Left bumper | Reverse intake |
| Right trigger | Fire catapult (it returns automatically when released) |
| A | Toggle field-centric / robot-centric |
| **Hold** B | Auto-drive to launch position |
| **Hold** X | Auto-drive to human player station |
| **Hold** Right bumper | Auto-drive to the gate and push it open |
| Y | Reset odometry pose (robot in the corner reset position) |

Letting go of B, X or right bumper cancels the path and gives control back to the driver. *(`TeleOpMain` only; `TeleOpManual` has only the driving, intake and catapult controls.)*

## Getting started

1. Clone the [Pedro Pathing Quickstart](https://pedropathing.com/), which this project is forked from. It comes with the FTC SDK and the Pedro Pathing setup.
2. Copy this code into `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/`.
3. Make sure `build.dependencies.gradle` uses the versions listed in [Dependencies](#dependencies). The latest versions have different APIs.
4. Build and deploy to the Robot Controller from Android Studio.
5. Create a hardware configuration that uses the names in [Hardware](#hardware).
6. Run the `Tuning` OpMode and update `pedroPathing/Constants.java` with your robot's values. The tuning values and field poses in this repo are for my robot.

## How the pieces fit together

- **Subsystems** wrap the hardware and expose simple methods (`setPower`, `intakeArtifact`, etc.).
- **Commands** implement Ivy's `Command` interface and declare the subsystems they need (`requirements()`), so the scheduler won't let two commands control the same subsystem at once.
- **Autonomous** routines are built from `sequential(...)` and `race(...)` command groups that combine Pedro path following (`follow(...)`) with `AutoLaunch` / `AutoIntake`. Racing a path against `waitMs(...)` acts as a timeout so a stuck path can't stall the whole auto.
- **`Storage`** holds static fields that keep their values between OpModes, which is how TeleOp knows where the robot finished auto and which alliance it's on.

## What I'd change (and am changing next season)

This was my first robot, and looking back, these are the design problems I'm fixing in next season's code:

- **An Auto Builder instead of copy-pasted autos.** The four goal-side autonomous OpModes are almost identical files, and each red version applies `.mirror()` by hand dozens of times. The version of Pedro Pathing this code uses didn't have a pose factory for mirroring poses by alliance, so the mirroring had to be done by hand. Every copy is another place for a bug to hide. To cut down on bugs, I want to build an Auto Builder that takes the alliance as a parameter and handles the mirroring in one place, so each auto OpMode is only a few lines. The auto-drive shortcuts in `TeleOpMain` would use it too.
- **Stringly-typed state.** The alliance is stored as the string `"Red"` or `"Blue"`. An `enum` would make a typo like `"red"` impossible to compile, instead of a silent bug on the field.
- **State that's fragile between OpModes.** Passing the pose from auto to TeleOp through static fields works, but it silently resets to the defaults if the Robot Controller app restarts between matches.
